# Meta Method Discovery：记住经验，也记住适用边界

以下为**使用合成数据实际运行的功能演示**，不是客户案例或真实用户效果研究。保存确认与培训反馈由测试夹具模拟；排班计算和预测误差为实际执行结果。可用作 README、发布帖或演示脚本。

## 案例一：上次有用，这次先检查条件

**场景**：为三个人安排三天值班，每人一次，并遵守各自可用时间。

程序实际枚举可行分配，并逐项检查每天覆盖、人员可用及每人一次。达标后，以合成测试身份确认保存这条 SUCCESS 经验。新进程能从 Markdown 文件中读取和检索它。

**新问题**：“现在增加夜班，但 A 没有夜班资质，能照搬旧班表吗？”

**按 Skill 的复用判断**：不能照搬。历史经验验证的是旧约束；保留建模思路，补上夜班资质约束后重新求解。新班表尚未生成，不能说已经满足新要求。

**可宣传的一句话**：

> Meta Method Discovery不只记住上次的解法，也保留它当时成立的条件。

展示重点：实际保存→新进程读取→检索返回待复核条件→Agent解释为什么不能照搬。

## 案例二：失败经验，也能成为下次的提醒

**场景**：训练数据为 `[10,10,10,10]`，固定历史三点均值预测之后两个点，实际值为 `[30,30]`。

实际预测为 `[10,10]`，MAE=20，超过演示预先设定的 MAE≤5 标准。因此记录为 FAILURE，而不是因为输出了预测就标成功。这个阈值是演示设定，不是行业标准。

确认保存后，新进程检索到原记录及失败提示。新问题仍是“促销导致需求突然跳升”，Agent应指出历史失败条件再次出现，不把旧均值法当成已验证有效推荐；应重新处理变化并回测。

**可宣传的一句话**：

> 个人方法库不只收藏成功，也保留失败原因，帮助下次检查是否重蹈覆辙。

展示重点：真实误差→FAILURE记录→检索保留失败边界。这个例子不证明均值法在所有预测中无效，也没有实际验证替代模型。

## 案例三：更容易理解，不等于成绩已经提高

**场景**：合成反馈设定为“分段文字复述让学员觉得更容易理解，但测验成绩没有提高”。没有真实参与者或真实培训试验。

记录为 PARTIAL_SUCCESS，证据类型为 user_feedback；不能改写成“客观证明培训有效”。

**新问题**：“接下来只能单向发通知，不允许收集回答，也没有反馈渠道，能直接复用吗？”

**按 Skill 的复用判断**：不能直接复用需要回答与反馈的完整流程。应说明当前渠道与历史条件不符，而不是只因都叫“培训”就套用。

**可宣传的一句话**：

> 保留“哪里有帮助、哪里没达标”，让经验比一句“有效”更具体。

展示重点：部分成功与主观证据类型→新条件冲突→拒绝机械复用。

## 三个案例共同演示的用户控制

- 仅预览及拒绝确认时，实际临时知识库没有创建文件。
- 测试夹具确认具体内容后，保存为独立 Markdown + YAML 文件。
- 独立 Python 进程能读取同一 memory_id，验证不依赖原 Python 对象。
- 更新后 version=2，保留 version=1 的历史；精确重复不新建记录。
- 另一合成用户查询为空；这仅验证接口路径隔离，不等于操作系统级保密。
- 经测试夹具确认删除后，活动库中的记录与嵌入历史消失，新进程检索为空。

为了公开演示，目录中保留了获准的**合成记录快照与导出副本**。删除验证针对活动临时知识库，不会删除这些明确导出的演示材料，也不声称删除外部备份。

## 推荐发布文案

> **Meta Method Discovery：让用过的方法，留下可复用的经验。**
>
> 实际使用后，经你确认保存问题、步骤、反馈和适用条件。下次遇到相似任务，先找回相关经验，再检查能不能复用。成功值得参考，失败也有提醒价值；你可以查看、更新、导出或删除记录。
>
> 本演示用合成数据展示实际存储与跨进程检索。方法效果取决于具体任务，适用性由 Agent 复核。

建议优先演示案例一与案例二：一个展示经验复用，一个展示失败教训；案例三补充解释反馈与验证的区别。

## 验证范围

3/3场景的存储断言通过，运行结果见 demo-output 下各目录 results.json。复用判断是主 Agent 对已知合成场景的定性审核，不是独立模型盲测；“新进程”不等于已经证明任意宿主的新 Agent 会话都会自动发现知识库。未向真实个人库写入任何演示记录。

复现：在项目根目录运行 `python -X utf8 examples/run_memory_demos.py`。脚本重新创建临时活动库，保存公开合成证据，不访问默认用户知识库。
